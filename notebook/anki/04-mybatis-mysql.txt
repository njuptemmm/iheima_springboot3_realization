MyBatis 是什么？	半自动 ORM 框架。<br>特点：<br>1. SQL 和 Java 代码分离（XML 或注解写 SQL）<br>2. 参数、结果自动映射<br>3. 不像 Hibernate 全自动生成 SQL，开发者能完全控制 SQL<br>4. 更适合复杂查询、大厂业务
MyBatis 里 #{} 和 ${} 的区别？	#{param}：预编译占位符 → 变成 ? → 防 SQL 注入<br>${param}：直接字符串拼接 → 有注入风险<br>只有 ORDER BY 列名、表名等**非值**位置才用 ${}，且必须做白名单校验（本项目 CourseTools.queryCourses 就是这样处理排序字段的）。
MyBatis 里 resultType 和 resultMap 区别？	resultType：字段名与属性名一致时自动映射（简单场景）<br>resultMap：手动指定映射规则（复杂场景、关联查询、集合映射）<br>resultMap 支持：<br>- id/result（基本映射）<br>- association（一对一）<br>- collection（一对多）
MyBatis 一级缓存 vs 二级缓存？	一级缓存：<br>- SqlSession 范围<br>- 默认开启<br>- 同一 session 内相同查询走缓存<br>二级缓存：<br>- Mapper 命名空间范围（跨 SqlSession）<br>- 默认关闭，需 &lt;cache/&gt; 标签开启<br>- 分布式环境不推荐（一致性问题）
MyBatis 的执行流程？	1. 加载配置 → 构建 SqlSessionFactory<br>2. 通过 Factory 打开 SqlSession<br>3. 通过 Mapper 接口调用方法<br>4. Executor 执行 SQL<br>5. StatementHandler 处理 JDBC Statement<br>6. ParameterHandler 设置参数<br>7. ResultSetHandler 处理结果集
MyBatis-Plus 相比原生 MyBatis 增加了什么？	1. BaseMapper：内置 CRUD 方法（selectById、insert、updateById）<br>2. IService：Service 层通用方法<br>3. QueryWrapper / LambdaQueryWrapper：条件构造器<br>4. 代码生成器<br>5. 分页插件（PaginationInnerInterceptor）<br>6. 逻辑删除、乐观锁、自动填充字段<br>本项目 CourseTools.queryCourses 用 QueryChainWrapper。
MyBatis-Plus 的 @TableName、@TableId、@TableField 用途？	@TableName("course") - 类到表的映射<br>@TableId(type=IdType.AUTO) - 主键，指定生成策略<br>@TableField("student_name") - 字段驼峰与下划线映射<br>本项目实体 Course/School/CourseReservation 都用了这些。
MyBatis 里怎么解决 N+1 问题？	场景：查 100 篇文章，每篇又查一次作者 = 101 次 SQL。<br>解决：<br>1. 用 &lt;association&gt; / &lt;collection&gt; 的 join fetch（一条 SQL 搞定）<br>2. IN 查询批量拉取<br>3. MyBatis 的懒加载（fetchType="lazy"）+ &lt;settings&gt; 里 lazyLoadingEnabled=true
MyBatis 动态 SQL 常用标签？	&lt;if&gt;、&lt;choose&gt;/&lt;when&gt;/&lt;otherwise&gt;<br>&lt;where&gt;（自动处理 WHERE 关键字和多余 AND）<br>&lt;set&gt;（UPDATE 时自动处理逗号）<br>&lt;trim prefix suffix prefixOverrides&gt;<br>&lt;foreach&gt;（循环，常用于 IN 查询）
数据库三大范式？	1NF：每列不可再分（原子性）<br>2NF：满足 1NF + 非主键字段完全依赖主键（消除部分依赖）<br>3NF：满足 2NF + 非主键字段之间无传递依赖（消除传递依赖）<br>实际项目常做**反范式**：为了性能加冗余字段。
MySQL 存储引擎？	InnoDB（默认）：<br>- 支持事务、行锁、外键<br>- 聚簇索引（数据和索引在一起）<br>- 崩溃恢复<br>MyISAM（老）：<br>- 不支持事务、表锁<br>- 查询快（不维护事务/MVCC）<br>- 现在几乎不用
MySQL 索引底层结构？	B+ 树<br>特点：<br>1. 非叶子节点只存索引不存数据（分支多、树矮）<br>2. 叶子节点用双向链表连接（支持范围查询）<br>3. 数据都在叶子层<br>为什么不用 B 树？B 树非叶子也存数据 → 树更高 → 磁盘 IO 更多。
聚簇索引 vs 非聚簇索引？	聚簇索引（InnoDB 主键索引）：<br>- 数据和索引在一起<br>- 叶子节点就是数据行<br>- 一张表只有一个<br>非聚簇索引（辅助索引）：<br>- 叶子节点存主键<br>- 查完辅助索引要**回表**（再查一次主键索引拿完整数据）
什么是覆盖索引？	查询的字段都在索引里，不需要回表。<br>例：INDEX idx_name_age(name, age)，SELECT name, age FROM user WHERE name=?<br>直接从辅助索引拿到 name, age，不用回表。<br>用 EXPLAIN 看：Extra 列显示 Using index。
最左前缀原则？	联合索引 (a, b, c)：<br>- WHERE a=? ✅ 用到<br>- WHERE a=? AND b=? ✅ 用到<br>- WHERE a=? AND b=? AND c=? ✅ 全用到<br>- WHERE b=? ❌ 用不到（跳过 a）<br>- WHERE a=? AND c=? ⚠️ 只用到 a
索引失效的常见场景？	1. LIKE '%xxx'（前导模糊）<br>2. 索引列上做运算或函数（WHERE age+1=20）<br>3. 类型转换（varchar 列传数字）<br>4. OR 连接的条件里有列没索引<br>5. IS NULL / IS NOT NULL（部分情况）<br>6. 违反最左前缀
InnoDB 的事务隔离级别？	4 种：<br>1. READ UNCOMMITTED（读未提交）- 脏读<br>2. READ COMMITTED（读已提交）- 不可重复读<br>3. REPEATABLE READ（默认）- 幻读（InnoDB 用间隙锁解决）<br>4. SERIALIZABLE（串行化）
脏读、不可重复读、幻读的区别？	脏读：读到别的事务**未提交**的数据（提交后可能回滚）<br>不可重复读：同一事务内两次读同一行数据不一致（别人 UPDATE 了）<br>幻读：同一事务内两次范围查询结果集不同（别人 INSERT 了）
MVCC 是什么？	Multi-Version Concurrency Control（多版本并发控制）<br>InnoDB 实现：每行数据带隐藏字段：<br>- trx_id：事务 id<br>- roll_pointer：回滚指针，指向 undo log<br>读操作走 ReadView 判断可见性，不加锁。<br>让"读不阻塞写、写不阻塞读"。
InnoDB 的锁类型？	行级锁：<br>- 记录锁（Record Lock）：锁一行<br>- 间隙锁（Gap Lock）：锁两条记录之间的间隙<br>- 临键锁（Next-Key Lock）：Record + Gap，InnoDB 默认<br>表级锁：<br>- 意向锁（Intention Lock）：加行锁前的意向声明
死锁怎么产生？如何避免？	场景：事务 A 持有 lock1 想拿 lock2，事务 B 持有 lock2 想拿 lock1。<br>避免：<br>1. 统一加锁顺序（例如按主键升序）<br>2. 缩短事务<br>3. 避免大事务里嵌套用户交互<br>4. 设置合理超时<br>MySQL 会自动检测并回滚代价小的事务。
EXPLAIN 常看哪几列？	1. type：查询类型（system &gt; const &gt; eq_ref &gt; ref &gt; range &gt; index &gt; ALL）<br>2. key：实际用的索引<br>3. rows：预估扫描行数<br>4. Extra：Using index（覆盖）、Using filesort（排序）、Using temporary（临时表）<br>目标：不出现 ALL 全表扫、避免 filesort/temporary。
MySQL 里 count(*) count(1) count(列) 有区别吗？	InnoDB 里：<br>count(*) - 优化过，不取值直接算行数（最快）<br>count(1) - 类似 count(*)<br>count(column) - 跳过 NULL 值（慢）<br>用 count(*) 即可。
MySQL 里 in 和 exists 谁快？	看子查询和外查询的量：<br>- 外表大、子查询表小 → in<br>- 外表小、子查询表大 → exists<br>MySQL 8.0+ 会自动优化，不用死记。
如何优化慢 SQL？	1. EXPLAIN 分析<br>2. 建索引（覆盖、联合、最左前缀）<br>3. 避免 SELECT *<br>4. 拆大 SQL：一次 JOIN 太多表 → 分步查<br>5. 分页优化：LIMIT 100000,10 → WHERE id &gt; 上次最大 id LIMIT 10<br>6. 冷热分离、读写分离、分库分表
数据库连接池的意义？为什么用 HikariCP？	连接池：预先建立连接复用，避免每次请求建 TCP 连接（3 次握手 + 认证）的开销。<br>HikariCP 是 Spring Boot 默认，特点：<br>1. 性能最强（比 Druid 快）<br>2. 代码精简<br>3. 无锁设计<br>本项目 application.yaml 配了 spring.datasource.hikari.*
Druid 相比 HikariCP 的优势？	1. 内置 SQL 监控（WebStatFilter）<br>2. 内置防 SQL 注入（WallFilter）<br>3. 慢 SQL 记录<br>4. 中文文档友好<br>代价：性能略低、依赖多。<br>本项目没用 Druid。
MySQL 主从复制原理？	1. 主库：写操作记录到 binlog<br>2. 从库：I/O 线程从主库拉 binlog，写到本地 relay log<br>3. 从库：SQL 线程读 relay log 重放<br>用途：读扩展、备份、故障切换。<br>问题：主从延迟（异步复制）。
分库分表的时机？为什么？	数据量：单表超 500 万行或 2GB<br>QPS：数据库压力接近上限<br>方式：<br>1. 垂直分库：按业务拆（用户库、订单库）<br>2. 垂直分表：把大字段抽出（评论内容单独表）<br>3. 水平分表：按 id 或时间分片<br>工具：ShardingSphere、MyCat
MySQL 里 UPDATE 和 DELETE 加锁范围？	InnoDB 默认 REPEATABLE_READ 下：<br>UPDATE / DELETE 走**当前读**，加临键锁（Record + Gap）<br>如果 WHERE 走的是主键唯一索引且是等值 → 只加记录锁<br>如果 WHERE 是范围 → 加间隙锁避免幻读
乐观锁 vs 悲观锁？	悲观锁：假设会冲突，先加锁再操作（SELECT ... FOR UPDATE）<br>乐观锁：假设不冲突，提交时检查（版本号 / CAS）<br>MyBatis-Plus 的 @Version 就是乐观锁：<br>UPDATE ... SET version = version+1 WHERE id=? AND version=?<br>影响行数 = 0 就是被别人改过了。
